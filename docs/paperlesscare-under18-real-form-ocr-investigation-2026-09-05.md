### 1.3 OCRエンジンについての重要な注意

本調査のOCRは **macOS Vision framework** で実施しました。本番の PaperlessCare が使う **Google Cloud Vision API とは別エンジン**です。

| 転用できる | 転用できない |
|---|---|
| 帳票のラベル構成・並び順 | 具体的な誤認識パターン（`障害福祉廿一個` のような） |
| 縦書きラベルが読めない等の構造的特性 | 改行位置の細部 |
| ラベルの分割傾向（`及`/`び`/`印` 等） | 信頼度スコア |

**したがって、本報告書で「様式の構造」として述べた内容は確定情報ですが、「OCR文字列の細部」は Cloud Vision で再確認が必要です。**

### 13.2 「保護者」に関する重要な注意

ご指示の例に `guardianName` / `guardianAddress` がありましたが、**様式にはこれらに対応する行がありません**。

| **児童** | 実際にサービスを利用する子 | 子ども本人 |

### 14.1 方針

### 14.3 追加を推奨「しない」フィールド

| 候補 | 判断 | 理由 |
|---|---|---|
| `guardianName` | **不要** | 様式に「保護者」欄は存在しない。`name`（支給決定障害者等）と重複し、値の二重管理になる |
| `guardianAddress` | **不要** | 同上（`address` と重複） |
| `guardianBirthday` | **不要** | 同上（`birthday` と重複） |
| `recipientChildName` 等の別名 | **不要** | `childName` が既に正しく対応している |
| page6用の `contactInfoPlanSupport` | **不要** | ページごとに `formData` が独立しているため、既存の `contactInfo` で足りる |

### 14.4 改名の検討（今回は実施しない）

`name` / `birthday` / `address` は、様式上は「支給決定障害者等」の情報です。より正確な名前は次のとおりです。

```ts
name      → recipientName       // 支給決定障害者等 氏名
birthday  → recipientBirthday   // 支給決定障害者等 生年月日
address   → recipientAddress    // 支給決定障害者等 居住地
furigana  → recipientFurigana   // 支給決定障害者等 フリガナ
```

**しかし今回は改名を推奨しません。**

| 観点 | 評価 |
|---|---|
| 得られるもの | 可読性の向上のみ |
| 失うもの | 既存データとの互換コード（`lib/compat/` にもう1本）、`buildSummary`・一覧・編集画面の改修、回帰リスク |
| 現在の実害 | **なし**（1フィールド = 1様式行 で対応しており、意味のずれはない） |

**child実装を優先し、改名は必要になった時点で `legacyPage2.ts` と同じパターンで実施するのが合理的です。**

## 15. parser設計案

### 15.1 【F-6】現状のまま child を有効化した場合に起きること（検証済み）

`certType="child"` は専用parser未登録のため `parseFallback` が走ります。実際に実行した結果:

| ページ | `parseFallback` の結果 | 問題 |
|---|---|---|
| page1 | `number` / `address` / `name` / `birthday` / `disabilityType` / `issueDate` / `cityName` は取得 | **`childName` / `childBirthday` / `issuerAddress` が取得できない**（本人と児童を区別できない） |
| page2 | **`birthday: "令和7年4月1日"`** のみ | **支給期間の一部が「生年月日」フィールドに入る** |
| page3 | 同上 | 同上 |
| page6 | 同上 | 同上 |

`parseFallback` の該当箇所:

```ts
// src/app/t/[tenantId]/lib/parsers/parseCertText.ts
birthday: text.match(/(昭和|平成|令和)[^\n]*?日/)?.[0] || "",
```

ページ2〜8には和暦の**期間**が多数あるため、その先頭部分が `birthday`（生年月日）として保存されます。

**これは前フェーズで是正した「フィールド名と意味の乖離」と同種の汚染です。child専用parserを用意せずに有効化してはいけない、という強い裏付けになります。**

### 18.1 共通の前処理

### 18.2 page1 / page5（受給者証Ⅰ・Ⅱ）

### 19.1 現在確認できている範囲

### 19.2 自治体差が生じうる箇所

障害福祉サービス受給者証は省令様式が基本ですが、実務上は自治体ごとに次の差が生じえます。

| 差異 | 影響を受ける実装 | リスク |
|---|---|---|
| 印字される補足欄の有無（例: page7 のラベルなし空行に何を印字するか） | `mealProvisionStatus` の扱い | 中 |
| 問い合わせ先欄の有無・位置 | **page6 で実際に差が確認された** | **高**（既に顕在化） |
| サービス組数（3組 / 5組 等） | `serviceType1..8` の上限 | 中 |
| ページ構成・冊子の分割方法 | `PAGE_COUNT = 8` の前提 | **高** |
| 文言の細部（`支給市町村名` / `支給市区町村名`） | ラベル一致判定 | 低（現行実装は両方を見ている） |
| 縦書き / 横書きの違い | 本人・児童の判定 | 中 |

### 19.3 【重要】page6 の差は「18歳以上/未満の差」とは限りません

第10章で確認した page6 の「問い合わせ先」の有無は、次のどちらの可能性もあります。

| 解釈 | 内容 |
|---|---|
| (a) | **18歳以上版と18歳未満版の様式差**（同一自治体内での違い） |
| (b) | **異なる自治体の様式差**（たまたま紫と黄緑が別自治体のものだった） |

**本調査では区別できません。** 実装上は「child のときに問い合わせ先を表示する」で当面問題ありませんが、**(b) だった場合、同じ自治体の18歳以上版にも問い合わせ先がある可能性があります。** 第20章の確認事項に含めています。

### 19.4 現時点で取るべきスタンス

- **「全国共通」と仮定しない**
- 当面は「確認済みの様式に対応する」として実装し、**自治体差はOCRサンプルが増えた時点で吸収する**
- ラベル一致は**部分一致より前方一致・完全一致を優先**し、想定外の文言で誤マッチしないようにする
- 抽出に失敗しても**手入力で救済できる**現在のUI設計（`EditableCertCell`）は自治体差への有効な保険になっている

### 25.3 T-3 の補足（安全なフォールバック）

現在の `parseFallback` は、どのページに対しても人物フィールド（`name` / `birthday` / `address`）を埋めようとします。ページ2以降ではこれが**誤ったデータの発生源**になります（第15.1章）。

推奨する変更:

```ts
// イメージ
export function parseCertText(text, pageIndex, certType) {
  const normalized = normalizeText(text);
  const parser = getCertPageParser(certType, pageIndex);
  if (parser) return parser(normalized);

  // 専用parserが無い場合：
  // ページ1・5（識別情報ページ）だけは緩い抽出を許容し、
  // それ以外のページは空のフォームを返す（誤った値を入れない）。
  return isIdentityPage(pageIndex) ? parseFallback(normalized) : emptyFormData();
}
```

**これは adult の page5〜8 にも効きます**（現在は adult でも誤値が入っている可能性があります）。
